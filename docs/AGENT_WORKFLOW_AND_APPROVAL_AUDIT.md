## 1. Approval Architecture & Safety Rules

Under the assignment specification, an agent must differentiate between **autonomous read-only telemetry gathering** and **state-mutating operations**:

| Operation Category | Tools / Capabilities | Execution Policy | Approval Card Required? |
|---|---|---|:---:|
| **Telemetry Log Inspection** | `telemetry__search_logs` | Autonomous / Automatic | **NO** |
| **Deployment History Audit** | `telemetry__get_deployment_history` | Autonomous / Automatic | **NO** |
| **Operational Guidance Review** | `telemetry__read_resource` | Autonomous / Automatic | **NO** |
| **Release Checklist & Manifest** | `filesystem__read_text_file` | Autonomous / Automatic | **NO** |
| **Root Cause Synthesis & Advice** | Internal ReAct synthesis | Autonomous / Automatic | **NO** |
| **Service Catalog & Health Query** | REST API endpoints | Autonomous / Automatic | **NO** |
| **Incident Ticket Creation** | `telemetry__create_incident_ticket` | Gated by Operator HITL | **YES** |

## 2. Issues Discovered and Corrections Applied

### Defect A: Over-broad Trigger Condition in Offline ReAct Loop
- **Before:** `wants_ticket = any(k in norm_query for k in ("ticket", "propose", "remediate", "incident", "create ticket"))`
- **Impact:** Any inquiry including the word `"incident"` (such as *"Investigate payments-api incident"*) invoked `telemetry__create_incident_ticket`, forcing an unrequested approval card on normal read-only triage.
- **Fix:** Restrict trigger checks strictly to explicit user instructions:
  ```python
  wants_ticket = any(
      k in norm_query
      for k in (
          "create ticket",
          "propose ticket",
          "file ticket",
          "open ticket",
          "propose an incident ticket",
          "propose a ticket",
          "propose a critical incident ticket",
          "create incident ticket",
          "create an incident ticket",
      )
  )
  ```

---

### Defect B: UI Displaying Arbitrary Stale Approvals
- **Before:** `InvestigationsPage.tsx` fetched `fetchPendingApprovals()` and took `matched ? [matched] : pending.slice(0, 1)`.
- **Impact:** If an unresolved pending approval sat in the database from hours prior, every subsequent investigation—including purely read-only log searches—displayed an approval card.
- **Fix:** The frontend now inspects the current run's execution:
  ```typescript
  const hasPendingMutation =
    Boolean(response.pending_approval) ||
    response.tool_calls.some(
      (t) => t.tool.includes('create_incident_ticket') && (t.status === 'pending_approval' || t.status === 'pending')
    );

  if (hasPendingMutation) {
    // Show only the approval generated by this investigation
    setPendingApprovals(response.pending_approval ? [response.pending_approval] : [...]);
  } else {
    // Read-only investigation: absolutely no approval card
    setPendingApprovals([]);
  }
  ```

---

### Defect C: Duplicate Ticket Proposals Across Loop Iterations
- **Before:** When a mutation tool was paused by the approval gate (`status: pending_approval`), the ReAct loop returned the pending status to the model without removing the tool from the schema, causing the model to retry the mutation tool in subsequent iterations.
- **Fix:** In `orchestrator.py`:
  1. Updated `SYSTEM_PROMPT` with explicit instructions:
     *"Normal incident investigations, root cause analyses, log reviews, deployment inspections, and release readiness checks are strictly READ-ONLY. Do NOT call state-mutating tools for normal investigations... When a proposed action is submitted to the approval gate (status: pending_approval) or rejected by the operator, you must NOT attempt to call the mutation tool again."*
  2. In `investigate()`, once a mutation tool is called, `mutation_attempted = True` prevents the mutation tool from appearing in `available_tools` for subsequent iterations.
